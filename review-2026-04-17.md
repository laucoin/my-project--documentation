# Documentation review — 2026-04-17

Scope: glossary, functional/index, business-objects (core, document, operations, preparation, registration), all feature pages, README, AGENTS.

Findings are grouped by category and ordered by severity. File paths are relative to the repo root.

## 1. Contradictions and data consistency

### 1.1 Blocking — must fix

**`functional/features/pagination.md` is a stale duplicate of `options.md`.**
- Title on line 15 is `# Options` (not Pagination).
- The list of options is outdated: missing `COMMENT`, `COMPLETION_NOTICE`, `MOVEMENT`, `PREPARATION`.
- The dependency tree (lines 43–50) says `ALERT` depends on `COMMUNICATION`, which directly contradicts the current `options.md` (line 49) where every option is `(independent)`.
- Fix: either delete `pagination.md` or replace its content with real pagination documentation. If the project truly has a pagination page to write, nothing today documents pagination rules even though several `search-*` features mention pagination in passing.

**`functional/index.md` lists only four modules under Business Objects — Preparation is missing.**
- Lines 14–17 list `Core`, `Document`, `Operations`, `Registration`.
- `business-objects/preparation/` exists on disk and is documented in the glossary.
- Same list on the Features side (lines 19–22) is also incorrect: `features/index.md` doesn't group features by module at all, yet the links `/functional/features/core/`, `/functional/features/document/`, `/functional/features/operations/`, `/functional/features/registration/` are broken — no such subfolders exist.

**`functional/features/index.md` is missing a Document section.**
- Files `list-documents.md`, `upload-document.md`, `download-document.md`, `delete-document.md` exist but are not linked from the features index.

**`functional/features/index.md` is missing Preparation and Registration sections.**
- No entries for Form / Registration / Preparation sub-elements (menu, budget, planning, etc.) even though the business objects are fully documented.

**`features/index.md` links to `purge-orphan-registration.md`, which contains only `TODO`.**
- Line 131. Same thing for `technical/index.md` (contains only `TODO`). Either complete or remove the reference.

**Soft-delete state name `ACTIVE` is used in two restore flows where no `ACTIVE` state exists.**
- `features/restore-movement.md:43` — `Set movement status = ACTIVE`. Movement's soft-delete state per glossary is `HIDDEN`; the restore should flip it back to `VISIBLE`, not `ACTIVE`.
- `features/restore-communication.md:49` — same problem for communication.
- Same shape error in `features/enable-activity.md:48` (`status = ACTIVE` — activity statuses are `DISABLED | AVAILABLE | NOT_AVAILABLE_YET | NO_MORE_AVAILABLE`, none of which is `ACTIVE`).
- Pick either `VISIBLE` (the counterpart of `HIDDEN`) or just delete the explicit status assignment and describe the soft-delete toggle semantically.

**Asymmetric allowed-roles between enable-X and disable-X.**
- `disable-activity.md:31`, `disable-group.md`, `disable-participant.md:26`, `disable-vehicle.md:31` all allow `PROJECT_ADMIN` + `PROJECT_MANAGER`.
- The matching `enable-activity.md:30`, `enable-group.md:30`, `enable-participant.md:24`, `enable-vehicle.md:30` allow only `PROJECT_ADMIN`.
- Either a manager can both disable and re-enable, or they can do neither. Pick one.

### 1.2 Medium — vocabulary / frontmatter drift

**Movement frontmatter inconsistent about `MOVEMENT` option.**
- `business-objects/operations/movement.md:7` declares `required_options: MOVEMENT`.
- All matching features (`search-movements.md`, `create-movement.md`, `edit-movement.md`, `hide-movement.md`, `restore-movement.md`) have an empty `required_options:`.
- Either the business object is wrong (movements are a core capability, not optional) or the features must all declare `MOVEMENT` in their frontmatter.

**Communication business object missing `required_options`.**
- `business-objects/operations/communication.md` frontmatter has no `required_options`, but the glossary (line 93) says Communication requires the `COMMUNICATION` option. Add it.

**Alert requires `COMMUNICATION` — unclear.**
- `features/search-alerts.md:21` and `features/create-alert.md:21` say `Requires the **ALERT** option (and **COMMUNICATION**)`.
- `functional/features/options.md:49` lists both as independent.
- `business-objects/operations/alert.md` doesn't require `COMMUNICATION`.
- Decide: is COMMUNICATION a hard dependency of ALERT or only used when an alert has a thread? If soft, remove `(and COMMUNICATION)` from the feature files; if hard, add it to `options.md` dependency tree and to the alert business object.

**`delete-organization.md` and `delete-project.md` list `modules: [core, operations]`.**
- Organization and Project both live in `core` only; no operations concept is touched directly by the delete itself. Fix: `modules: [core]`.
- If the intent is "delete also purges related operations data", state that explicitly in the description section, not in `modules`.

**Options naming not listed in the glossary.**
- `glossary.md` enumerates option flags only in narrative form (`GROUP`, `ALERT`, `COMMUNICATION`, `COMMENT`, `PREPARATION`, `REGISTRATION`, `COMPLETION_NOTICE`) but `ACTIVITY`, `VEHICLE`, `MOVEMENT` also exist in `options.md` and are referenced from business objects. Either move the canonical option list to the glossary as a bulleted section, or link to `options.md` from the glossary's "Options" section.

**Movement business-object mixes "transaction" and "movement".**
- `business-objects/operations/movement.md:35, 37, 40` call it a "transaction". Everywhere else it's a "movement". Replace with "movement".

**`project.md:65` relationship to Preparation is garbled.**
- Text: `A project contains zero or many preparation (zero to one project + zero to one by project)`.
- Conflicts with `preparation/index.md:45–48` ("at most one per project"). Rephrase as: `A project has at most one preparation.` (And optionally: or one per group if attached at group level.)

**Registration visibility rule undocumented in Core.**
- `business-objects/registration/index.md:50` and `registration.md:60` say a participant/group created via a pending registration is hidden from other modules. But `business-objects/core/participant.md` and `group.md` never mention this hidden-by-registration state. Add a one-liner there so someone reading only the participant spec doesn't miss it.

**Soft-deleted alerts — state not documented.**
- `glossary.md:164–173` maps every entity to a soft-delete state except Alert. `alert.md` itself never states a soft-delete state. Either add `HIDDEN`/`CANCELED` explicitly, or say alerts are not soft-deletable and can only be `CANCELED`.

**Participant/Group/Vehicle presence statuses are inconsistent.**
- Participant: `NOT_HERE`, `NO_MORE_HERE`, `NOT_ARRIVED_YET`.
- Vehicle: `NOT_HERE`, `NO_MORE_HERE`, `NOT_USED_YET`.
- Group: `SHOULD_BE_HERE`, `NO_MORE_HERE`, `NOT_ARRIVED_YET`.
- Activity: `AVAILABLE`, `NOT_AVAILABLE_YET`, `NO_MORE_AVAILABLE`.
- Four near-parallel state machines with three different vocabularies for "after its window" (`NO_MORE_HERE`, `NO_MORE_AVAILABLE`), two for "before its window" (`NOT_ARRIVED_YET`, `NOT_USED_YET`, `NOT_AVAILABLE_YET`), and one orphan (`SHOULD_BE_HERE`). Pick one axis — presence or availability — and normalize.

**"Eligible participant statuses" in `movement.md:92–96` don't match participant.md's status table.**
- `movement.md` lists `NOT_ARRIVED_YET`, `IN`, `OUT` as movement-eligible statuses; but `participant.md:85–89` never uses `IN` or `OUT` — it uses `NOT_HERE` / `NO_MORE_HERE`. Align the two.

### 1.3 Minor — duplication / link hygiene

- `project.md:62` and `operations/index.md` ER diagram describe the communication-per-movement relationship in different terms. Pick one phrasing.
- `glossary.md:155–158` uses `INTERNAL` / `EXTERNAL` notice types, consistent with `completion-notice.md`. Good.

## 2. Clarity of the rules

- **Support Profile 1h window is undocumented in `profile.md`.** The glossary mentions the 1-hour fixed window, but `business-objects/core/profile.md` (the canonical spec) never states it. A developer reading only the business object will miss the rule.
- **Movement `reason` field.** In `movement.md` the field appears in "Main attributes" (line 54) without a list of allowed values. The enumeration only shows up later in 119–148. Either move the enumeration up or add "See the Reason section below" in the attribute row.
- **Guest participant's 2-movement lifecycle is stated in `glossary.md` and `participant.md` but absent from `movement.md`.** Add it to the constraints section of Create/Edit movement.
- **"Movement is immutable" vs. edit-movement feature.** `movement.md:34–42` says immutable; `edit-movement.md` lets you edit. The rule is "edit = soft-delete + recreate". Use the exact phrase "edit = soft-delete + recreate" consistently everywhere (business object, feature, glossary) instead of switching between "tampered with", "corrected replacement", "soft-delete + recreate".
- **Create Communication constraints.**
  - `create-communication.md:46` says the movement must be "in progress: an `OUT` movement of `REGISTERED` participants".
  - `communication.md:22` says it's any movement with an activity.
  - `options.md:83` and `pagination.md:75` say it's any currently `OUT` movement.
  - Pick one and propagate.
- **Alert state machine is not specified.** `alert.md` lists three statuses (`IN_PROGRESS`, `RESOLVED`, `CANCELED`) but no allowed transitions. Add a mermaid state diagram or a table.
- **Preparation validation workflow is not specified.** `options.md:123` says `DRAFT → IN_REVIEW → VALIDATED / REJECTED` but `preparation/index.md` does not. Which can revert? Who has the right to move a preparation to each state?
- **Location "active period" undefined.** `location.md:43–46` forbids overlapping active periods of the same preparation but never defines what the active period field is. Add it to Main attributes.
- **Planning slot override rules are incomplete.** `planning.md:48–53` says a day can inherit or override; doesn't say if a day can remove a slot inherited from the typical day, add a new slot, etc.
- **Edit Project constraints section is empty.** `edit-project.md` lists "No automatic profile creation" but doesn't state what fields can be edited (name? options? dates?). Mirror the Create Project constraints or explicitly state `Same as create-project, minus the automatic profile`.
- **Edit Group constraints section header is odd.** `edit-group.md:33`: `Constraints (differences with creation)` and then says "No additional constraints". If there are no differences, just write `Same as create-group`.
- **`create-organization.md:31` says `is_strict_auth` and `is_main` are "required".** Required-with-default or required-from-user? State defaults explicitly.
- **Vehicle driver relationship is unclear.** `vehicle.md:23` says the movement records who drives; `movement.md` doesn't describe a driver attribute. Either add a Driver attribute to movement, or reword vehicle.
- **Preparation attached to group vs project is stated three ways.** Glossary says "project or group (not both)"; `preparation/index.md` says "mutually exclusive"; `project.md:65` says something garbled (see 1.2). Single source of truth needed.
- **Tag management authority not stated.** Glossary says tags are project-scoped; `comment.md` says "managed at project level". Which role can create/rename/delete a tag? Add to `roles.md` or `comment.md`.
